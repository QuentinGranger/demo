# Instructions métier : Calendriers Fortnite France & Europe

Les règles de surveillance technique dans `shared-health.md` et la politique courante du dépôt remplacent toute ancienne référence de santé ci-dessous. Exécuter Pokémon et Fortnite à chaque passage ; Harry Potter général une fois par jour. Les tâches séparées ont été regroupées à la demande de l'utilisateur le 26 septembre 2026.

Surveille Fortnite France/Europe et maintiens les calendriers et ledgers du repo QuentinGranger/demo. À chaque run, lis d'abord les politiques/états canoniques présents dans calendars/, notamment : fortnite-change-ledger.json = FORTNITE_CHANGE_LEDGER_FR_V2 ; fortnite-change-engine-france.json = FORTNITE_CHANGE_ENGINE_FR_V2 ; fortnite-notification-outbox-france.json = FORTNITE_NOTIFICATION_OUTBOX_FR_V1 ; fortnite-change-index-france.json = FORTNITE_CHANGE_INDEX_FR_V1 ; sources/watchlist ; taxonomie + lore V2 ; service V2 ; season/pass engine V2 ; competitive ledger/engine/deadline/participants ; physical events/venues/access engine V2 ; ticketing V2 ; ICS validation. Ces fichiers et leurs moteurs conservent toutes les règles détaillées existantes : anti-rumeur, source authority, IDs stables, append-only history, projections sélectives, rappels, deadlines, qualification/LCQ, pass windows, access/admission, scarcity, lore claims et validation RFC5545. Ne rétrécis aucun de ces périmètres.

CHANGE/NOTIFICATION V2 EST UNE BARRIÈRE OBLIGATOIRE POUR TOUTE ALERTE. Un Git SHA, checked_at, last_verified_at, timestamp de crawl, DTSTAMP/LAST-MODIFIED sans changement métier, index, ordre JSON, folding ICS, badge fraîcheur, score interne ou simple nouvelle source confirmant le même fait ne constitue pas un changement utilisateur.

Pour tout delta : 1) résoudre domain + stable subject_key + scope_key ; 2) fresh-read l'état canonique et la tête causale ; 3) calculer state_fingerprint + transition_fingerprint ; 4) si l'état voulu existe déjà ou si le même transition fingerprint est rejoué contre le même causal parent, NO-OP ; 5) sinon créer une nouvelle subject_revision et un change_id causal stable. Cette chaîne doit permettre une vraie récurrence SOLD_OUT->AVAILABLE->SOLD_OUT sans la confondre avec un replay du même SOLD_OUT.

Chaque change accepté reçoit notification_disposition figée : BASELINE, SILENT_POLICY, ELIGIBLE_NOW, ELIGIBLE_WHEN_DUE, CONDITION_BLOCKED, STALE ou NOT_APPLICABLE. Un changement silencieux ne devient jamais rétroactivement notifiable parce qu'une politique change plus tard. Les faits présents au baseline 2026-08-19T15:49:00Z restent connus/silencieux après restart/re-crawl.

CROSS-DOMAIN EFFECT COLLAPSE : évite qu'un même fait alerte une fois via ticketing, une fois via physical access et une fois via CALENDAR_PROJECTION. Utilise causal_source_change_ids/user_effect_id quand plusieurs écritures représentent le même effet utilisateur. CALENDAR_PROJECTION ne renotifie jamais un effet déjà porté par un changement canonique sous-jacent. Une deuxième source officielle confirmant le même effet enrichit l'évidence, pas le nombre d'alertes.

OUTBOX — EXACTLY-ONCE INTENT / AT-MOST-ONCE ATTEMPT : notification identity = user_effect_id ou sorted change_ids + notice_kind + audience_key + channel_key. Avant toute émission : coalescer les changements liés ; figer payload + payload_fingerprint + render_version ; fresh-fetch fortnite-notification-outbox-france.json et son blob SHA ; si notification_key est déjà consommée, stop. Sinon ajouter l'intent si absent + un delivery_event RESERVED, puis update GitHub avec CE SHA frais comme compare-and-swap. SEUL un run dont la réservation RESERVED a été persistée avec succès peut émettre l'alerte.

CONCURRENCE : si l'update outbox échoue pour conflit SHA, abandonne le payload stale, fresh-fetch et re-évalue tout. Si la clé est désormais consommée : silence. Si elle est encore absente et la condition toujours vraie, un nouveau CAS construit depuis l'état frais est autorisé. Jamais deux émissions depuis la même notification_key.

APRÈS ÉMISSION : fresh-fetch outbox puis append SENT via CAS. Si SENT ne peut pas être persisté, RESERVED reste terminalement consommé : ne jamais renvoyer. RESERVED >30 min sans SENT => append UNKNOWN_DELIVERY via CAS ; aucun retry automatique. La priorité est d'éviter absolument un doublon même si cela peut exceptionnellement manquer une alerte. Un retry de UNKNOWN_DELIVERY/RESERVED exige intervention explicite, jamais automatique.

RAPPELS FUTURS : ne crée JAMAIS un intent/RESERVED plusieurs heures/jours avant l'heure de rappel. DORMANT/ARMED/PLANNED restent dans leurs domain ledgers. Au trigger réel : fresh-read faits/versions/conditions ; si encore actionnable, alors seulement construire l'intent, CAS reserve, puis émettre. Si invalidé avant l'échéance, aucun outbox intent n'est créé. Aucun backfill passé.

COALESCING : fenêtre 10 min avant réservation pour changements réellement liés au même sujet/effet (ex. lieu exact + doors time, ticket return + catégorie rouverte, reschedule + deadline recalculée, season start + downtime explicitement lié). Ne fusionne jamais événements indépendants, participants différents, annulation puis réactivation, ni deux occurrences de cycle distinctes. Une fois RESERVED, groupe/payload immuables.

WRITE IDEMPOTENCY : notification dedupe et Git-write dedupe restent séparés. Avant chaque update/delete GitHub d'un fichier existant, fresh-fetch ce chemin et utilise son SHA courant. Si conflit, ne rejoue jamais le vieux contenu ; re-fetch/recompute. Aucun commit pour état sémantiquement identique. Pour ICS, projected_business_fingerprint exclut DTSTAMP/LAST-MODIFIED/folding/header-only/freshness expiry ; SEQUENCE+1 uniquement si business VEVENT change réellement. Si crash après write possiblement réussi, fresh-fetch la cible et compare l'état désiré avant toute tentative.

RECONCILIATION : fortnite-change-index-france.json est dérivé/jetable. Rebuild depuis change ledger + outbox si divergent. Toute intent doit référencer des change_ids existants. consumed_keys doit être dérivable exclusivement des delivery_events RESERVED/SENT/UNKNOWN_DELIVERY. Chaîne causale : revision N>1 pointe vers revision N-1 du même subject_scope. UNKNOWN_DELIVERY/UNKNOWN_COMMIT_STATE sont anomalies d'audit, jamais prétexte à rejouer automatiquement.

DOMAINES EXISTANTS À CONTINUER : saisons/passes/Ranked, service/downtime, compétitif EU exhaustif avec projection sélective et qualification/LCQ, participants, billetterie, événements physiques France/Europe avec admission/access/venue, lore/taxonomie, watchlist, calendriers global/updates/competitive. Conserve toutes les politiques détaillées de leurs fichiers moteurs. Anti-rumeur absolu ; sources officielles/directes selon authority ; aucun fait inventé.

PERMANENT CROSS-CALENDAR HEALTH OBSERVER V2 — appliquer calendars/calendar-health-policy.json = CROSS_CALENDAR_HEALTH_POLICY_FR_V2, calendars/calendar-health-state.json = CROSS_CALENDAR_HEALTH_STATE_FR_V2 et calendars/calendar-health-heartbeat.json = CROSS_CALENDAR_HEALTH_HEARTBEAT_FR_V2. Cette veille est l'un des DEUX observateurs horaires déclarés ; elle n'est pas une autorité unique.

HEALTH INCIDENT DEDUPE : incident_key = health|franchise-or-system|incident_code|stable_subject. Nouvel incident => fresh-fetch state + SHA, OPEN une fois. Même incident ouvert => silence. Impact accru => ESCALATED une fois. Résolution => RECOVERED une fois. Recalculer overall/franchise/observer_state. Ne jamais réactiver silencieusement une automation désactivée volontairement.

VALIDATION : après modification respecter scripts/validate_calendar_health.py et tous les validateurs Fortnite existants. Les fichiers de health eux-mêmes ne modifient aucun VEVENT/SEQUENCE et ne constituent pas un changement métier.
